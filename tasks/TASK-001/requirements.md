# TASK-001 — Требования: Training Sessions Workspace

Источник: `frontend-accelerator-assessment/FRONTEND_ASSESSMENT_SPEC.md`. Для уточнения деталей использованы `API_CONTRACT.md`, `MOCKING_GUIDE.md`, `EVIDENCE_PROTOCOL.md`, на которые ссылается спека.
Статус: требования задокументированы, готовы к следующему шагу (см. «Готовность»).
Опциональные пункты спеки в требования **не включены** (см. раздел «Исключено как опциональное»).

## 1. Цель

Frontend-рабочее пространство, в котором оператор тренерского бизнеса (занятой тренер, который регулярно просматривает расписание, решает вопросы вместимости и создаёт новые занятия) может **найти, просмотреть и создать** запланированные тренировочные сессии.

- Только frontend. Бэкенд не реализуется; контракт API из `API_CONTRACT.md` реализуется через MSW за заменяемой клиентской границей.
- Приоритет интерфейса: быстрое сканирование и предсказуемые действия, а не декоративность. Операционный инструмент, без маркетинговой композиции.

## 2. Критерии приёмки

Формат: ID — проверяемое утверждение. Способ проверки: **A** = автотест, **B** = браузер, **R** = ревью/осмотр.

### 2.1. Рабочее пространство сессий

- **AC-1.1** (B) Есть маршрут или эквивалентный навигируемый экран со списком сессий.
- **AC-1.2** (A, B) Для каждой сессии в списке видны: название, тип, статус, время начала, длительность, тренер, локация, вместимость, количество записанных.
- **AC-1.3** (A, B) Поиск по строке находит сессии по названию, имени тренера или локации без учёта регистра.
- **AC-1.4** (A) Поиск и фильтр выполняются запросом `GET /api/sessions` с параметрами `query` и `status`; фильтрация полного списка на клиенте не засчитывается. `meta.total` отражает отфильтрованный результат.
- **AC-1.5** (A, B) Можно выбрать ровно один статус из `scheduled | full | cancelled | completed`; список сужается до сессий этого статуса.
- **AC-1.6** (A, B) Действие «сбросить все фильтры» очищает поиск и статус и возвращает полный список.
- **AC-1.7** (B, R) Статусы `scheduled`, `full`, `cancelled`, `completed` различимы между собой **не только цветом** (например, текстовая метка или иконка).
- **AC-1.8** (B) Открытие сессии не теряет текущий контекст списка: после возврата из деталей поиск и фильтр остаются в прежнем состоянии.

### 2.2. Детали сессии

- **AC-2.1** (A, B) Детали показывают всю информацию из списка плюс: описание, заметки тренера, сводку по вместимости, контакты тренера (имя, email), время создания и время последнего обновления.
- **AC-2.2** (B) Отсутствующие описание и заметки (`null`) отображаются корректно, без «null» и пустых заголовков-сирот.
- **AC-2.3** (B) Детали полностью доступны с клавиатуры (открытие, перемещение фокуса, закрытие/возврат).
- **AC-2.4** (B) Возврат из деталей возвращает пользователя к предыдущему состоянию списка.
- **AC-2.5** (B) Если выбран формат, допускающий deep link (маршрут), прямой переход по адресу деталей открывает эту сессию. Если формат не допускает, это фиксируется как ограничение в решениях и финальном отчёте.

### 2.3. Создание сессии

Поля формы: название, тип сессии, дата, время начала, длительность, тренер, название локации, адрес локации, вместимость, видимость, необязательные описание и заметки тренера.

Валидация:

- **AC-3.1** (A, B) Название: 3–80 символов после trim.
- **AC-3.2** (A, B) Дата и время вместе дают начало **в будущем** по локальному часовому поясу пользователя.
- **AC-3.3** (A, B) Длительность: целое число от 30 до 240 минут.
- **AC-3.4** (A, B) Вместимость: целое число от 1 до 100.
- **AC-3.5** (A, B) Тренер обязателен.
- **AC-3.6** (A, B) Название локации: 2–80 символов после trim.
- **AC-3.7** (A, B) Адрес локации: 3–120 символов после trim.
- **AC-3.8** (A, B) Заметки тренера: не более 500 символов.
- **AC-3.9** (B, R) Ошибки полей показаны рядом с соответствующими контролами и программно связаны с ними; при необходимости есть понятная ошибка уровня формы.

Отправка:

- **AC-3.10** (A, B) Пока запрос в ожидании, повторная отправка невозможна (нет дублирующих `POST`).
- **AC-3.11** (A, B) При ошибке API (в т.ч. `500 CREATE_SESSION_FAILED` и `400 VALIDATION_FAILED`) введённые значения сохраняются; пользователь понимает, что произошло и что делать дальше. `fieldErrors` из ответа показываются у полей.
- **AC-3.12** (A, B) При успехе пользователь видит явное подтверждение (без необходимости гадать, создана ли сессия).
- **AC-3.13** (A, B) Созданная сессия появляется в рабочем пространстве через последующие запросы списка и деталей. Если активные фильтры её скрывают, есть явное действие «открыть новую сессию» или «сбросить соответствующие фильтры».
- **AC-3.14** (A, B) Если не удалось загрузить тренеров (`coaches-error`), форма не делает вид, что может отправить корректный выбор тренера: это видно пользователю, отправка с невалидным выбором невозможна, есть путь восстановления.

### 2.4. Обязательные состояния UI (наблюдаемые и тестируемые)

- **AC-4.1** (A, B) Начальная загрузка.
- **AC-4.2** (A, B) Список с данными.
- **AC-4.3** (A, B) Сессий нет совсем (`empty`): отдельное сообщение и путь дальше (создать сессию).
- **AC-4.4** (A, B) Фильтры ничего не нашли: сообщение **отличается** от «сессий нет», есть сброс фильтров.
- **AC-4.5** (A, B) Ошибка списка (`list-error`): понятное сообщение и повтор/восстановление.
- **AC-4.6** (A, B) Ошибка деталей (`details-error`): понятное сообщение и повтор/восстановление.
- **AC-4.7** (A, B) Ошибка тренеров (`coaches-error`).
- **AC-4.8** (A, B) Создание: ожидание, успех, ошибка валидации, ошибка сервера.

### 2.5. Моки и граница API

- **AC-5.1** (R, A) Приложение делает обычные HTTP-запросы по путям из `API_CONTRACT.md`: `GET /api/sessions`, `GET /api/sessions/:sessionId`, `GET /api/coaches`, `POST /api/sessions`.
- **AC-5.2** (A) Mock-слой поддерживает сценарии `normal`, `empty`, `list-error`, `details-error`, `coaches-error`, `create-error` из `fixtures/mock-scenarios.json`.
- **AC-5.3** (R) Выбор сценария находится на границе мока; компоненты представления и API-клиент не импортируют JSON-фикстуры и не ветвятся по именам сценариев.
- **AC-5.4** (A) `POST /api/sessions` возвращает `201`, генерирует идентификатор и временные метки, использует выбранного тренера из `coaches.json`; состояние хранится только в памяти. Ошибки валидации контракта дают `400 VALIDATION_FAILED` с `fieldErrors`.
- **AC-5.5** (A, R) Фикстурные `startsAt`, `createdAt`, `updatedAt`, `cancelledAt` сдвигаются на разницу между реальным текущим моментом и `referenceNow` из `fixture-clock.json`; сдвиг выполняется только на границе мока. Тесты замораживают время и применяют то же преобразование. Компоненты получают только валидные ISO 8601 UTC-строки.
- **AC-5.6** (R) Компоненты не содержат разбросанных «сырых» транспортных вызовов; замена MSW на реальный бэкенд не требует переписывания компонентов представления.
- **AC-5.7** (R) У серверного состояния и состояния запросов есть осознанный владелец, без дублирования источников истины.
- **AC-5.8** (R, A) Даты разбираются и нормализуются в одной явной точке; пользователю показываются в его локальном часовом поясе.
- **AC-5.9** (R) Эндпоинты не выдуманы, формы ответов не изменены молча; предлагаемые изменения контракта записаны отдельно.

## 4. Исключено как опциональное (не входит в требования)

- фильтрация по типу сессии;
- синхронизация фильтров с URL;
- пагинация (при этом ответ сохраняет `page: 1`, `pageSize: 10`);
- отмена сессии, включая восстановление после `403` и `409`; эндпоинт `POST /api/sessions/:sessionId/cancel`;
- режим только для чтения и входной параметр прав доступа;
- фоновое обновление;
- проверка планшетного размера;
- сценарии `create-conflict`, `cancel-forbidden`, `cancel-conflict`, `read-only`, `slow-refresh`, `unknown-session`;
- оптимистичные обновления с откатом;
- дополнительные автотесты и визуальные регрессионные тесты;
- календарь и сохранённые фильтры.

Опциональная работа не компенсирует недостающее обязательное поведение.

## 5. Допущения

Факты берутся из спеки. Допущения ниже **не подтверждены** и не должны попасть в living specs как установленная истина.

- **A-1** Часовой пояс пользователя — часовой пояс браузера; отдельной настройки часового пояса нет.
- **A-2** Статус `full` приходит из API (в виде значения `status`), клиент не вычисляет его самостоятельно из `bookedCount` и `capacity`.
- **A-3** Фильтр статуса «ни один» (все статусы) является состоянием по умолчанию; выбор ровно одного статуса исключает множественный выбор.
- **A-4** Список по умолчанию содержит 5 записей из `fixtures/sessions.json`, без пагинации; клиент не обязан обрабатывать более 10 записей.
- **A-5** Сброс мока при перезапуске приложения допустим (состояние в памяти).
- **A-6** Видимость сессии (`public | invite-only`) отображается в деталях и создаётся в форме; отдельного требования показывать её в списке нет.
- **A-7** Значения по умолчанию в форме создания (тип, видимость) не заданы спекой и определяются на этапе UI-дизайна.
- **A-8** Для 404 на деталях (`SESSION_NOT_FOUND`) достаточно общего состояния ошибки деталей, так как отдельный сценарий (`unknown-session`) опционален.

- Риск: «дата в будущем» зависит от локального часового пояса и текущего времени, поэтому тесты валидации чувствительны к часам.
