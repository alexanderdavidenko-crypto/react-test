## 3. Граница API-клиента (`src/shared/api`)

Экспорт:
- Типы контракта один в один.
- Четыре функции, последний аргумент `{ signal?: AbortSignal }`: `getSessions({ query?, status? }, opts)`, `getSessionDetails(sessionId, opts)`, `getCoaches(opts)`, `createSession(request: CreateSessionRequest, opts)`.
- Результат (решение 5=B): `{ ok: true, data } | { ok: false, error }`. Отмена не является ошибкой данных и сигнализируется отдельно (отдельный признак/исключение отмены); хуки её игнорируют и статус не меняют.
- Виды `error` (классы с явными полями, без parameter properties из-за `erasableSyntaxOnly`):
  - `ApiError`: `kind = "api"`, `status`, `code`, `message`, `fieldErrors?`.
  - `NetworkError`: `kind = "network"` (fetch отклонён не по abort).
  - `ResponseShapeError`: `kind = "malformed"`, `status?`, причина (не-JSON, неверная форма, неожиданный статус, неизвестный enum, невалидная дата).
- Предикат `isApiError(e, code?)`.

Внутри: единственное место вызова `fetch`; сборка URL через `URLSearchParams` (`query` после trim, пустой не отправляется; `status` пустой не отправляется; других параметров, в том числе `scenario`, нет); заголовки `Accept: application/json`, для POST ещё `Content-Type: application/json`; `encodeURIComponent` для id; разбор ответа, мапперы, преобразование ошибок.

Чего нет: импорта фикстур и ветвления по сценариям (AC-5.3); ретраев, таймаута, кэша, дедупликации; логики дат и часовых поясов (это `shared/lib/datetime`); знания о списке тренеров и допустимости `coachId`; зависимостей от React.

## 4. Единый алгоритм разбора ответа

1. `fetch` отклонён: abort -> сигнал отмены; иначе `NetworkError`.
2. Ожидаемый успешный статус (`200` для GET, `201` для POST): читать JSON; не JSON или неверная форма (включая HTML `index.html` со статусом 200) -> `ResponseShapeError`.
3. Не 2xx: разобрать `{error:{code,message,fieldErrors?}}`; удалось -> `ApiError` (код сохраняется как есть, не группируется и не переименовывается); не удалось -> `ResponseShapeError` с сохранённым HTTP-статусом.
4. Неожиданный 2xx (например `200` вместо `201`, `204`) -> `ResponseShapeError`.
5. Валидация формы (решение 6=A): проверяются все рендеримые поля `SessionSummary`/`SessionDetails`/`CoachSummary`/`meta`, типы значений, ISO-даты. Неизвестное значение enum (`type`, `status`, `visibility`) = malformed. Лишние поля игнорируются. Частично валидные данные не показываются.
6. В сообщения ошибок клиент не добавляет чувствительных деталей (URL, stack). `message` сервера доступно в `ApiError`; пользовательские тексты решает ui-designer.

## 5. Матрица состояний и ошибок

Состояния хуков (D-4): `idle | loading | success | error`.

| Операция | idle | loading | success | error | Восстановление |
|---|---|---|---|---|---|
| `GET /api/sessions` | до первого запуска | запрос с `query`/`status` из URL; предыдущий запрос отменён | `200`, форма проверена; `data=[]`/`total=0` тоже success (UI различает "нет сессий" и "нет совпадений" по наличию фильтров) | `400 INVALID_FILTER` (не ожидается из-за нормализации URL, но обрабатывается как ошибка списка); `500 SESSIONS_UNAVAILABLE`; network; malformed | `retry()` с текущими фильтрами |
| `GET /api/sessions/:id` | нет `id` | запрос; смена `id` отменяет предыдущий | `200 SessionDetails`, даты проверены | `404 SESSION_NOT_FOUND` (по A-8 общее состояние ошибки деталей, но код сохраняется); `500 SESSION_DETAILS_UNAVAILABLE`; network; malformed | `retry()`; для 404 повтор допустим, но малоосмыслен (решает UI) |
| `GET /api/coaches` | форма не открыта | запрос при открытии формы | `200`; пустой `data` = success, но валидного `coachId` нет | `500 COACHES_UNAVAILABLE`; network; malformed | `retry()` по действию пользователя, без автоповтора |
| `POST /api/sessions` | не отправлялась; после ошибки повторная отправка разрешена | флаг pending блокирует вторую отправку; POST не отменяется (10=A) | `201 SessionDetails`; затем refetch списка владельцем (D-4) | `400 VALIDATION_FAILED` + `fieldErrors` (может быть без ключей -> ошибка уровня формы); `500 CREATE_SESSION_FAILED`; `409 COACH_SCHEDULE_CONFLICT` (общий `ApiError`); network; malformed | ручная повторная отправка введённых значений; автоповтора и заявлений об идемпотентности нет |

Особые случаи:
- Сетевая или malformed-ошибка при POST: исход неизвестен (запрос мог дойти до сервера). Клиент не утверждает "сессия не создана"; формулировка и действие — за ui-designer (раздел 12).
- Неизвестный `error.code` -> `ApiError` без спецлогики.
- Ключ `fieldErrors`, не соответствующий полю формы -> ошибка уровня формы (D-7).

## 6. Политика дат

- Из API: `startsAt`, `createdAt`, `updatedAt`, `cancellation.cancelledAt` принимаются только как ISO 8601 UTC с `Z`; миллисекунды допускаются (решение 7=B для входа: маппер принимает оба формата). Строка без `Z` или со смещением -> malformed (assumed, В-2). В приложении значения остаются строками; `Date` создаётся только внутри `shared/lib/datetime`.
- В API (форма -> `startsAt`): локальные дата и время (часовой пояс браузера, A-1) -> один `Date` -> ISO UTC строка **без миллисекунд** (`YYYY-MM-DDTHH:mm:ssZ`, как в фикстурах; решение 7=B). Проверка "в будущем" по тому же `Date` против текущего момента (в тестах время заморожено).
- Крайние случаи datetime-модуля: несуществующее локальное время (переход на летнее время) детектируется обратным разбором и даёт ошибку поля; неоднозначное время (осенний переход) допустимо; невалидная дата (30 февраля) — ошибка поля.
- Показ только через `shared/lib/datetime` (Intl). Сдвиг фикстур только в `mocks/` (AC-5.5).
- Ошибки: плохая дата в ответе -> `ResponseShapeError` (не "Invalid Date" в UI); ошибка даты в форме — клиентская ошибка поля; `fieldErrors.startsAt` с сервера показывается как остальные.

## 7. Моки (`src/mocks`)

Состав на уровне контракта:
- Один набор обработчиков `msw` 2.14.6 для браузера (`setupWorker`) и тестов (`setupServer` из `msw/node`).
- Хранилище в памяти: копия фикстур после сдвига времени; функция сброса для тестов (`server.resetHandlers()` store не сбрасывает, это обеспечивается setup'ом).
- Fixture clock: при старте `delta = now - referenceNow`; сдвигаются все поля из `timestampFields`, включая вложенный `cancellation.cancelledAt`. В тестах `now` из замороженных часов, то же преобразование.
- Задержка `normal` 250 мс (из `defaultLatencyMs`); в тестах задержка отключаема (параметр конфигурации мока), без отдельного сценария.
- `GET /api/sessions`: `status` вне четырёх значений -> `400 INVALID_FILTER` (assumed); фильтры применяются до `meta.total`; `meta.page=1`, `meta.pageSize=10`; данные не усекаются, новые сессии в конец, `total` = фактическое число (8=A; порядок assumed).
- `GET /api/sessions/:id`: известный id (включая созданные) -> детали; неизвестный -> `404 SESSION_NOT_FOUND`.
- `GET /api/coaches`: `data` из `coaches.json`.
- `POST /api/sessions`: проверяет обязательные поля, значения `type`/`visibility`, положительные `durationMinutes` и `capacity`, существование `coachId` в `coaches.json`, валидный ISO `startsAt` (с миллисекундами и без); клиентские диапазоны и "в будущем" на сервере не проверяются. Ошибки -> `400 VALIDATION_FAILED` с `fieldErrors` (ключи = имена полей запроса); нечитаемое тело -> `400` без `fieldErrors`. Успех: `201`, сгенерированный id (assumed `ses_<n>`), `createdAt=updatedAt=now`, `status=scheduled`, `bookedCount=0`, `cancellation=null`, `coach` из `coaches.json`, нормализованные значения; сессия сразу видна в списке и деталях.
- Тексты `message` берутся из `mock-scenarios.json` как есть.
- Bootstrap (dev, `main.tsx`) дожидается готовности worker до первого рендера. Незарегистрированные запросы к `/api` в режиме мока считаются ошибкой (`onUnhandledRequest: "error"`), для ассетов Vite — bypass.

### `npm run build` и `npm run preview` при моках только в dev (решение 1=C)
Ожидаемые последствия (все НЕПРОВЕРЕНО запуском):
- Если bootstrap подключает `mocks/` условным динамическим `import()` под `import.meta.env.DEV`, Vite исключает мок-код и фикстуры из прод-бандла. `tsc -b` при этом всё равно типизирует `src/mocks`.
- `public/mockServiceWorker.js` копируется в `dist` как статический файл, но не регистрируется.
- `vite preview` не знает о `/api`; по умолчанию отдаёт `index.html` со статусом 200 для неизвестных путей (SPA fallback). Клиент получает HTML вместо JSON -> `ResponseShapeError`; список, детали, тренеры и создание в preview в состоянии ошибки. POST на preview ожидаемо вернёт не-2xx ответ без контрактного тела (поведение не проверялось).
Решение: моки только в dev; в README описать, что `preview` без бэкенда показывает ошибки (ожидаемо), а запуск для проверки — `npm run dev`; автотест: ответ HTML со статусом 200 -> `ResponseShapeError`. Вариант с флагом сборки `VITE_ENABLE_MOCKS` отвергнут как противоречащий D-8.

## 8. Q-3: выбор сценария (закрыто, API-часть)

- Источник и приоритет: `?scenario=<name>` в URL, затем `VITE_MOCK_SCENARIO`, затем `normal`. Читается один раз при старте внутри `src/mocks` до первого рендера; смена значения после старта на мок не влияет; перезагрузка с тем же URL даёт тот же сценарий.
- Допустимые имена: ровно шесть обязательных. Остальные (в том числе опциональные из JSON: `create-conflict`, `cancel-forbidden`, `cancel-conflict`, `read-only`, `slow-refresh`, `unknown-session`) и пустые значения невалидны.
- Невалидное имя в URL (2=A): `console.warn` с перечнем допустимых имён, откат на значение из `VITE_MOCK_SCENARIO`; если оно тоже невалидно или не задано — `normal`. В консоль выводится выбранный сценарий и источник (`url | env | default`). Приложение не падает.
- Только dev (`import.meta.env.DEV`). В тестах URL и переменная не используются; сценарии задаются `server.use` поверх базовых обработчиков.
- Сочетание с маршрутизацией и фильтрами: `scenario` соседствует с `query`/`status`; `shared/router` его имени не знает, но сохраняет посторонние параметры при навигации (AC-1.14, A-12); домен читает только `query` и `status`; сброс фильтров удаляет только их, `scenario` остаётся; редирект неизвестного пути на `/sessions` сохраняет `search`; клиент `scenario` в запросы не передаёт. НЕПРОВЕРЕНО: порядок старта (мок читает URL раньше редиректа роутера) — проверяется при реализации.
- Без утечки в компоненты: компоненты, хуки и `shared/api` не импортируют `mocks/` и не читают `scenario`/`VITE_MOCK_SCENARIO`; единственный потребитель `mocks/` в рантайме — dev-bootstrap `main.tsx`; контролов выбора сценария в UI нет. Проверка на ревью: grep по `scenario` и `fixtures` вне `src/mocks` и тестового setup должен быть пуст.

## 9. Q-6: `coaches-error` и создание (закрыто, API-часть)

- Гарантия ставится в `useCreateSession`/фиче `create-session`, а не в `shared/api` (4=A): отправка (вызов `createSession`) не выполняется, пока `coaches.status !== "success"` или выбранный `coachId` не входит в список; дополнительно блокировка в UI (за ui-designer).
- Валидный `coachId`: непустая строка, равная `id` элемента последнего успешного ответа `GET /api/coaches`. Свободный ввод, значение по умолчанию "первый тренер" и id из других сессий не допускаются. Пустой список = валидного `coachId` нет.
- Повтор загрузки: `useCoaches().retry()` по действию пользователя, без автоповтора; новый запрос отменяет незавершённый. Если выбранный ранее `coachId` отсутствует в обновлённом списке, он перестаёт быть валидным (сброс выбора — решение ui-designer).
- Сервер всё равно проверяет `coachId` (`400 VALIDATION_FAILED`, `fieldErrors.coachId` — assumed); клиентская проверка серверную не заменяет и не скрывает.
- Не решается здесь: блокировать форму целиком или только поле тренера (UI-часть Q-6, раздел 12).

## 11. Предложения по контракту

Пусто. Изменений путей, полей, форматов и кодов ошибок не предлагается; новых эндпоинтов не вводится. Пробелы контракта оформлены как допущения (раздел 2) и вопросы владельцу (раздел 13). Если ответы владельца потребуют изменения контракта, это оформляется отдельным предложением и требует одобрения оценщика (раздел "Contract Authority" контракта).

## 12. Передаётся ui-designer

- Q-6 (UI-часть): блокировать форму целиком или только выбор тренера при `coaches-error`; расположение и текст "Повторить загрузку тренеров"; поведение при пустом списке тренеров; сброс выбора, если после повтора выбранный тренер исчез. API-гарантии из раздела 9 фиксированы.
- Тексты ошибок: список/детали (включая отдельную формулировку для `SESSION_NOT_FOUND`), тренеры, `VALIDATION_FAILED` (поля и уровень формы; ключ `fieldErrors` без поля -> ошибка формы), `CREATE_SESSION_FAILED`, `NetworkError`, `ResponseShapeError`. Серверный `message` доступен, но не обязан показываться дословно.
- Сетевая ошибка или malformed-ответ при POST: исход неизвестен. Текст не должен утверждать "сессия не создана"; предложить повтор и проверку списка; повторная отправка допустима, но контракт идемпотентности не даёт (возможен дубль).
- Смена входа в хуках: при смене фильтров или `id` запрос отменяется; нужно решить, что показывать между ними (предыдущие данные списка на время `loading` допустимы; детали другого `id` показывать нельзя). Одновременно `idle` для деталей без `id`.
- Пустой успешный список: различие "нет сессий" и "нет совпадений" выводится из наличия фильтров, не из API.

## 14. Стратегия тестов на границе API

Общее: `msw/node` с теми же обработчиками, что и в браузерном моке; `server.use` для сценариев; фикстуры и сдвиг времени только в `mocks/`; время заморожено; store сбрасывается между тестами; задержка мока в тестах нулевая. Поведение, а не детали реализации (AC-9.2); число тестов остаётся в ориентире 6–7, граничные проверки оформляются таблично и добавляются только при оправданном риске.

На границе `shared/api`:
1. HTML со статусом 200 и не-JSON -> `ResponseShapeError` (имитация `preview`, решение 1=C).
2. `HttpResponse.error()` -> `NetworkError`.
3. `400`/`500` с телом контракта -> `ApiError` с `code` и `fieldErrors`; не-2xx без контрактного тела -> `ResponseShapeError` с HTTP-статусом.
4. Неверная форма 200 (неизвестный enum, не-ISO дата, нет `meta`) -> `ResponseShapeError`.
5. Запрос списка уходит ровно с `query`/`status`, без пустых значений и без `scenario`.
6. Отмена: ответ отменённого запроса не меняет состояние, в том числе под StrictMode.

На границе с фичами (встраиваются в тесты D-9, новых тестов по возможности не создают):
- при `coaches-error` нажатие "отправить" не порождает `POST` (Q-6);
- `create-error`: ввод сохранён; отдельно `400` с `fieldErrors` через `server.use`;
- `list-error`/`details-error`: переход ошибка -> успех после `retry` через `server.use` (сценарии статичны);
- `empty`: после `POST` список показывает созданную сессию (9b);
- сброс фильтров не удаляет `scenario` (в тесте URL-навигации).

Не покрывается автотестами: реальный `<dialog>`, реальный `preview` без бэкенда, реальные задержки (browser-verify).
