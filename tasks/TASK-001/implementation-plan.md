## 1. Текущее и целевое поведение

Сейчас: шаблон Vite. `src/App.tsx` — демо-счётчик, `src/main.tsx` — StrictMode и `<App />` без bootstrap мока. Нет роутера, API-клиента, `src/mocks`, `src/shared`, тестов, скрипта `test`. Шаблонные `index.css` (`#root`, `body`, `color-scheme: light dark`) и `App.css` задают раскладку, не подходящую рабочему пространству. `public/mockServiceWorker.js` и `msw` 2.14.6 присутствуют.

Цель:
- `/sessions`: рабочее пространство со списком сессий, поиском и фильтром по одному статусу. Параметры уходят в `GET /api/sessions` (`query`, `status`), URL — единственный источник истины фильтров, список переживает перезагрузку и Назад/Вперёд.
- `/sessions/:id`: модалка деталей (нативный `<dialog>`) поверх списка, с общим query string, deep link, возврат на прежний URL списка.
- «Create session»: вторая модалка с формой (без URL), клиентская валидация, pending-защита, ошибки полей и формы, экран успеха с «Open session», «Create another», «Close».
- Все состояния (AC-4.x), MSW-мок со всеми шестью сценариями, fixture clock, stateful `POST`.
- Адаптив 1440×900 и 390×844, доступность, живые регионы.
- Дев-режим запускается `npm run dev` с моком, `?scenario=<name>` выбирает сценарий.

## 2. Файлы

### 2.1. Создание

**`src/shared/lib/datetime.ts`** — единственная точка работы с датами.
Контракт (на уровне описания): разбор и проверка ISO 8601 UTC (с `Z`, миллисекунды допустимы); форматирование для списка (`Aug 3, 18:00`), деталей (с коротким именем пояса) и служебных строк; `localToIsoUtc(date, time)` возвращает ISO UTC без миллисекунд либо признак ошибки (невалидная дата или несуществующее локальное время, определяется обратным разбором); `isFuture(iso, now)`. Остальной код `new Date(...)` и `toLocale*` не вызывает.

**`src/shared/api/`**
- `types.ts`: типы контракта один в один (`SessionType`, `SessionStatus`, `Visibility`, `CoachSummary`, `LocationSummary`, `SessionSummary`, `SessionDetails`, `SessionsResponse`, `CoachesResponse`, `CreateSessionRequest`).
- `errors.ts`: `ApiError` (`kind="api"`, `status`, `code`, `message`, `fieldErrors?`), `NetworkError` (`kind="network"`), `ResponseShapeError` (`kind="malformed"`, `status?`, причина), `isApiError(e, code?)`. Явные поля, без parameter properties и enum (`erasableSyntaxOnly`).
- `mappers.ts`: проверка формы ответа (все рендеримые поля, типы, enum, ISO-даты через `datetime`), неизвестный enum = malformed, лишние поля игнорируются.
- `client.ts`: `getSessions({query?, status?}, opts)`, `getSessionDetails(id, opts)`, `getCoaches(opts)`, `createSession(request, opts)`; `opts = { signal?: AbortSignal }`. Результат `{ok:true,data} | {ok:false,error}`, отмена отдельным признаком. Единственное место вызова `fetch`; URL через `URLSearchParams`; `query` после trim, пустые значения не отправляются, других параметров (включая `scenario`) нет; `encodeURIComponent` для id; заголовки `Accept`, для POST ещё `Content-Type`; алгоритм разбора ответа по api-integration раздел 4.

**`src/shared/router/`**
- Хук чтения `location` (path + search) с подпиской на `popstate` и собственные навигации.
- `navigate(to, { replace?, state? })`.
- Разбор пути `/sessions/:id`; неизвестный путь -> `replace` на `/sessions` с сохранением search.
- Чтение и запись search-параметров с сохранением посторонних параметров нетронутыми.
- Флаг «из приложения (из списка)» в `history.state`.
- Доменных имён параметров не знает. Вложенных маршрутов, loader-ов, гвардов нет.

**`src/mocks/`**
- `clock.ts`: `delta = now − referenceNow`, сдвиг полей `startsAt`, `createdAt`, `updatedAt`, `cancellation.cancelledAt`; в тестах `now` из замороженных часов, то же преобразование.
- `store.ts`: копия фикстур после сдвига, хранение в памяти, функция сброса для тестов (в том числе стартовое пустое состояние для `empty`).
- `handlers.ts`: четыре эндпоинта по api-integration раздел 7 (фильтры в хендлере до `meta.total`, `400 INVALID_FILTER` для `status` вне четырёх значений, `404 SESSION_NOT_FOUND`, stateful `POST` с `201`, `400 VALIDATION_FAILED` с `fieldErrors`, генерация id и timestamps, тренер из `coaches.json`). Задержка 250 мс в `normal`, отключаема параметром в тестах.
- `scenarios.ts`: ровно шесть имён; приоритет `?scenario=`, затем `VITE_MOCK_SCENARIO`, затем `normal`; невалидное имя -> `console.warn` и откат; в консоль выбранный сценарий и источник; только `import.meta.env.DEV`; тексты `message` из `mock-scenarios.json` как есть; статичные сценарии ошибок.
- `browser.ts` (`setupWorker`, `onUnhandledRequest: "error"` для `/api`, bypass для ассетов Vite) и `node.ts` (`setupServer` из `msw/node`).
- Единственный потребитель в рантайме — dev-bootstrap `main.tsx`; в тестах — `src/test/setup.ts`.

**`src/features/sessions/`**
- `filters.ts`: чтение `query` и `status` из search, нормализация (trim; невалидный `status` = нет фильтра и не уходит на сервер), запись только этих двух параметров, сброс удаляет только их; «активны ли фильтры».
- `copy.ts`: тексты фичи (ui-design раздел 10), функции склонения и подстановки.
- `useSessions.ts`: `useSessions(filters)` -> `{status: idle|loading|success|error, data, error, retry}`; отмена при смене фильтров и размонтировании, игнор устаревших ответов; при смене фильтров прежние данные сохраняются на время `loading` (признак «обновляется»). Принимает сигнал-инвалидатор (счётчик или `refetch`) для обновления после создания.
- `useSessionDetails.ts`: `useSessionDetails(id|null)`; при смене `id` старые данные сбрасываются; `retry`.
- Компоненты: `SessionsPage` (шапка, панель инструментов: поиск с debounce `replace`, нативный select статуса, «Clear filters»; область списка с состояниями; постоянный live-регион), `SessionList`/`SessionRow` (ссылка `<a href>` с растянутой областью, переход через `navigate` с флагом «из списка», модификаторы клика не перехватываются), `StatusBadge` (иконка `aria-hidden` + текст), `SessionDetailsDialog`, `CapacitySummary`.

**`src/features/create-session/`**
- `copy.ts`: тексты формы и успеха.
- `validate.ts`: чистая функция `validate(values, now) -> errors by field` по AC-3.1–3.8 и UI-правилам (в т.ч. пара Date/Start time, несуществующее время); серверные `fieldErrors` накладываются поверх.
- `useCoaches.ts`: `useCoaches()` -> статус, `data`, `retry`; запрос при открытии формы; хранит «последний успешный список» для guard.
- `useCreateSession.ts`: `useCreateSession(coaches)` -> `{submit(values), status, error, fieldErrors, reset}`. Guard: `createSession` не вызывается, пока `coaches.status !== "success"` или `coachId` не входит в список; флаг pending блокирует повторный вызов; POST не отменяется; после успеха вызывается колбэк обновления списка.
- Компоненты: `CreateSessionDialog` (форма, подтверждение закрытия грязной формы, pending, блок формы, фокус), `Field` (метка, подсказка, ошибка, `aria-invalid`/`aria-describedby`, счётчик), экран успеха.

**`src/shared/ui/`** — только реально переиспользуемое (кандидаты: `Dialog` над `<dialog>`, `StateMessage`, `Button`, `LiveStatus`). Размещается здесь, если используется в обеих фичах; иначе остаётся в фиче.

**`src/app/`** — `App.tsx`: выбор маршрута (`/sessions`, `/sessions/:id`), локальное состояние открытости формы, колбэки «Open session» (навигация на `/sessions/{id}` с текущим search), «Clear filters» из экрана успеха, обновление списка после создания и после закрытия формы с неоднозначной ошибкой POST. Фичи друг друга не импортируют.

**`src/test/`** — `setup.ts` (подключение `msw/node`: `listen`/`resetHandlers`/`close`; сброс store; заморозка `Date`; полифил `showModal`/`close` для `<dialog>` при необходимости), `render.tsx` (рендер приложения с заданным начальным URL).

**Тесты:** интеграционный файл (7 тестов, раздел 3) и отдельный небольшой файл граничных тестов API-клиента (раздел 8).

### S8. Срез «создание» (вертикальный)
- Файлы: `features/create-session/*`, правки `app/App.tsx` (открытие формы, колбэки), общие компоненты `Dialog`, `Field`.
- Тесты (essential):

- Команды: `npm run lint`, `npm run build`, `npm run test` (после S0), `npm run dev`.

- Файлы: стили (`index.css`, `App.css`, стили фич), `README.md`.
- Тесты: нет новых автотестов (jsdom не проверяет вёрстку и фокус); браузерная проверка по разделу 5.

## 7. Зависимости и конфигурация, ставятся вручную

Ничего из перечисленного план не устанавливает и не правит; выполняет пользователь (шаг S0) после git-чекпоинта (решение 5=C).

Dev-зависимости (имена без версий): `vitest`, `@testing-library/react`, `@testing-library/user-event`, `jsdom`. `msw` 2.14.6 уже установлен, `msw/node` входит в пакет. `@testing-library/jest-dom` не добавляется (решение пользователя, architecture D-9); утверждения пишутся стандартными средствами vitest и запросами Testing Library.

Причина (AC-10.4): в репозитории нет раннера и DOM-окружения; AC-9.1/9.3 требуют автотестов поведения через ту же HTTP-границу (MSW). Компромисс: четыре dev-зависимости, jsdom не вычисляет layout и может неполно реализовывать `<dialog>.showModal()`, утверждения без jest-dom многословнее; вёрстка и реальный фокус проверяются в browser-verify. Новые зависимости не используются в рантайме приложения (AC-10.8).

Правки конфигурации:
- `package.json`: скрипт `test` (однократный запуск vitest). Команда `npm run test` появится после этой правки и установки.
- `vite.config.ts`: секция `test` (окружение jsdom, setup-файл `src/test/setup.ts`, при необходимости `globals`); для известности типа секции `test` потребуется импорт `defineConfig` из конфигурационного входа vitest либо эквивалент (способ подтверждается после установки).
- `tsconfig.app.json`: правка нужна только при использовании `globals` vitest (добавление типов) либо если не пройдёт импорт JSON-фикстур (`resolveJsonModule`, см. расхождение 13); в иных случаях не меняется. `tsconfig.node.json` включает `vite.config.ts`; правка нужна, только если типы vitest-конфига этого потребуют (НЕ ПРОВЕРЕНО).
- `src/test/setup.ts` — файл приложения, создаётся на S5 (не конфигурация); содержит подключение `msw/node`, сброс store, заморозку `Date`, полифил `showModal`/`close` при отсутствии метода.
- Другие конфигурации не меняются (AC-10.3). `.oxlintrc.json` не меняется; возможные замечания `lint` к тестовым файлам фиксируются как находки, без изменения правил без согласования.

НЕ ПРОВЕРЕНО (проверяется при реализации):
- наличие и полнота `HTMLDialogElement.showModal` в установленной версии jsdom;
- поведение фейковых таймеров (подмена только `Date` против полного фейка) совместно с MSW-задержкой, `userEvent` и debounce 300 мс;
- `resolveJsonModule` и импорт JSON вне `src/` под `tsc -b`;
- исключение мок-кода и фикстур из прод-бандла (`dist`);
- подхват `VITE_MOCK_SCENARIO` из окружения процесса Vite;
- порядок чтения `?scenario=` и редиректа роутера.

## 8. Дополнительные тесты по риску (не входят в обязательный набор AC-9.1)

Отдельно от 7 essential. Файл граничных тестов API-клиента — небольшой, отдельный (решение 6=B), помечается в самом файле и в `verification.md` как risk-based; AC-9.2 допускает больше тестов «при оправданном риске», обоснование — решение 1=C api-integration (preview без бэкенда) и риск неверной формы ответа.

Граничные тесты `shared/api` (api-integration раздел 14):
1. HTML со статусом 200 (имитация `preview`) и не-JSON -> `ResponseShapeError`.
2. `HttpResponse.error()` -> `NetworkError`.
3. `400`/`500` с телом контракта -> `ApiError` с `code` и `fieldErrors`; не-2xx без контрактного тела -> `ResponseShapeError` с HTTP-статусом.
4. Неверная форма 200 (неизвестный enum, не-ISO дата, нет `meta`) -> `ResponseShapeError`.
5. Запрос списка уходит ровно с `query` и `status`, без пустых значений и без `scenario`.
6. Отмена: ответ отменённого запроса не меняет состояние, в том числе под StrictMode.

Прочие risk-тесты:
- `datetime`: несуществующее локальное время, невалидная дата (30 февраля), «в будущем», формат `startsAt` без миллисекунд.
- `validate`: границы AC-3.1–3.8 таблично, если не покрыты T5.
- `details-error` и 404: сообщение, «Try again» (кроме 404), «Back to sessions»; переход ошибка -> успех через `server.use`.
- `empty` + `POST`: созданная сессия видна в списке.
- Активные фильтры скрывают созданную сессию: экран успеха, «Clear filters», «Open session».
- Подтверждение закрытия грязной формы («Keep editing», «Discard»).
- Сетевая или malformed-ошибка `POST`: текст не утверждает «не создана», закрытие формы запускает `refetch` списка.
- Отображение `null` для описания и заметок без слова «null».
- Лимит описания 1000 символов (по желанию, не обязателен).

Не покрывается автотестами (BV): реальный `<dialog>`, реальный `preview` без бэкенда, реальные задержки, вёрстка, контраст, фокус.

## 9. Зависимость плана от EVIDENCE_PROTOCOL

План не создаёт перечисленные ниже артефакты; он фиксирует, что они потребуются.

- Имя этого артефакта по протоколу: `tasks/TASK-001/implementation-plan.md` (решение 0=A).
- Порядок создания (§2, AC-11.6): артефакты планирования существуют до production-реализации. Источники: git-коммит с артефактами до coder, хэш в `workflow-log.md` отдельным небольшим коммитом, плюс история сессии (решение 5=C). Поле «Хеш чекпоинта» в `workflow-log.md` заполняет разработчик или роль, которой он это поручит; сам план `workflow-log.md` не правит.
- `workflow-log.md` (§3): записи ролей и ответов; время вносится из слов разработчика (AC-11.8).
- `review.md` (§4): вердикт code-reviewer; для каждой находки — resolved, accepted limitation, disputed или unresolved.
- `verification.md` или `final-report.md` (§5): каждая выполненная команда `test`/`build`/`lint` с рабочей директорией, кодом выхода и решающим выводом; пропущенные и заблокированные проверки; итоговый Git status/diff. Команда `npm run test` появится после S0; до этого фиксируются только `lint` и `build`.
- `browser-verification.md` (§6, AC-11.3, AC-11.4): URL, сессия адаптера, шаги, вердикт, владение сервером; матрица: заполненный список (1440×900 скриншот + снимок доступности; 390×844 скриншот + клавиатура/касание + переполнение), создание (валидация, защита от дублей, успех, обнаруживаемость), ошибка создания, `empty` и no-match, ошибка списка и одна из `details-error`/`coaches-error`; консоль, ошибки страницы, сеть; непроверенное названо явно.
- `evidence/` (§1): `populated-desktop.png`, `populated-mobile.png`, дополнительные скриншоты потоков.
- Сценарии (§7): для каждого из шести — способ выбора и итоговый URL (`/?scenario=<name>` или `VITE_MOCK_SCENARIO=<name> npm run dev`); контролов выбора сценария в UI нет, они не выдаются за продуктовую функцию.
- `final-report.md` (§8): только проверенные факты, новые зависимости с компромиссами, известные ограничения (непроверенное из раздела 7), допущения (A-13 и прочие).

## 10. Команды проверки (итог)

Существующие в `package.json`: `npm run dev` (ручной запуск и browser-verify), `npm run lint`, `npm run build` (`tsc -b && vite build`), `npm run preview` (ожидаемо показывает ошибки без бэкенда, README это описывает). Скрипта запуска с моками нет и не вводится (решение 4=A).

Появляются только после ручной установки и правки конфигурации (S0): `npm run test` (скрипт `test`).
