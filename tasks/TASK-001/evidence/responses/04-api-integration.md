### 2. Граница API-клиента (`src/shared/api`)

**Что экспортируется**
- Типы контракта один в один: `SessionType`, `SessionStatus`, `Visibility`, `CoachSummary`, `LocationSummary`, `SessionSummary`, `SessionDetails`, `SessionsResponse`, `CoachesResponse`, `CreateSessionRequest`, `ApiErrorBody`.
- Четыре функции. Каждая принимает последним аргументом `{ signal?: AbortSignal }`:
  - `getSessions({ query?, status? }, opts)`;
  - `getSessionDetails(sessionId, opts)`;
  - `getCoaches(opts)`;
  - `createSession(request: CreateSessionRequest, opts)`.
- Типизированные ошибки, не расширяя контракт:
  - `ApiError`: `kind = "api"`, `status`, `code`, `message`, `fieldErrors?`.
  - `NetworkError`: `kind = "network"`, `fetch` отклонён (нет сети).
  - `ResponseShapeError`: `kind = "malformed"`, `status`, причина. Покрывает: не-JSON при 2xx, неверная форма тела, не-JSON при 4xx/5xx.
  - Отмена (`AbortError`) не является ошибкой данных: наружу уходит как отдельный признак отмены. Хуки её игнорируют и не меняют статус.
- Вспомогательный предикат `isApiError(e, code?)`.

**Что внутри**
- Единственное место, где вызывается `fetch`.
- Формирование URL: query-параметры `query` (после trim, пустой не отправляется) и `status` (пустой не отправляется), через `URLSearchParams`.
- Заголовки: `Accept: application/json`; для `POST` ещё `Content-Type: application/json`. Других заголовков, авторизации, cookies нет (auth вне объёма).
- Разбор ответа, мапперы с проверкой формы и ISO-дат (D-6), преобразование ошибок.

**Чего нет**
- Нет импорта фикстур и ветвления по именам сценариев (AC-5.3).
- Нет ретраев, таймаута, кэша, дедупликации, локального хранилища.
- Нет логики "в будущем", локальных часовых поясов и форматирования (это `shared/lib/datetime`).
- Нет знания о тренерах из формы и о том, "допустим ли coachId" (это уровень фичи, см. Q-6).
- Нет зависимостей от React.

**Способ возврата ошибок:** функции возвращают значение при успехе и бросают типизированные ошибки, либо возвращают дискриминированный union. Это развилка №8 (ниже). Для хуков и тестов различие небольшое.

### 3. Единый алгоритм разбора ответа (для всех четырёх вызовов)

1. `fetch` отклонился не по abort → `NetworkError`. Отмена → сигнал отмены, ничего не показывать.
2. Статус 2xx и ожидаемый статус (`200` для GET, `201` для POST): тело читать как JSON. Не JSON или не соответствует форме (включая HTML-ответ `index.html` при 200) → `ResponseShapeError`.
3. Статус не 2xx: пробуем разобрать `{error:{code,message,fieldErrors?}}`. Если разобралось → `ApiError`. Иначе → `ResponseShapeError` с сохранённым HTTP-статусом (код "неизвестная ошибка", сообщение сервера не придумывается).
4. Неожиданный 2xx (например `200` вместо `201`, `204`): `ResponseShapeError`.
5. Клиент не использует `message` от сервера как единственный текст для пользователя без политики: тексты UI решает ui-designer, но `message` из ответа доступно в `ApiError` для вывода. Чувствительных деталей (stack, URL) в сообщения ошибок клиент не добавляет.

### 4. Матрица состояний и ошибок

Состояния хуков по D-4: `idle | loading | success | error`. Для GET: `idle` только до первого запуска (например, `useSessionDetails(null)` без id, форма закрыта); при смене входа перезапуск идёт в `loading`, прошлые данные при этом не очищаются или очищаются, решает ui-designer (подсказка: оставлять предыдущие данные нельзя, если они относятся к другому `id` деталей).

| Операция | idle | loading | success | error (код / вид) | Как восстановиться (на уровне API) |
|---|---|---|---|---|---|
| `GET /api/sessions` | нет входа/не запрошено (на практике сразу loading) | запрос с `query`/`status` из URL; предыдущий запрос отменён | `200`, форма проверена. `data=[]` и `meta.total=0` → success с пустыми данными (UI различает "нет сессий" и "нет совпадений" по наличию фильтров, это уровень UI) | `400 INVALID_FILTER` (не ожидается при нормализации URL, но обработать как ошибку списка); `500 SESSIONS_UNAVAILABLE`; network; malformed | `retry()` хука повторяет с текущими фильтрами |
| `GET /api/sessions/:id` | `id` отсутствует | запрос; при смене `id` отмена предыдущего | `200 SessionDetails`, форма и даты проверены | `404 SESSION_NOT_FOUND` (по A-8 общий вид ошибки деталей, но код сохранён, чтобы UI мог показать "не найдена" без "Повторить" при желании); `500 SESSION_DETAILS_UNAVAILABLE`; network; malformed | `retry()`; для 404 повтор бессмыслен, но допустим (решает UI) |
| `GET /api/coaches` | форма не открыта | запрос при открытии формы | `200`, `data` непустой. Пустой `data` (в контракте не запрещён) → success, но создание невозможно (см. Q-6) | `500 COACHES_UNAVAILABLE`; network; malformed | `retry()`, без автоповтора |
| `POST /api/sessions` | форма не отправлялась (между отправками тоже idle/error: после ошибки повторная отправка разрешена) | флаг pending блокирует вторую отправку (AC-3.10). Отмена запроса при закрытии формы не отменяет серверный эффект, и это не изображается откатом: см. вопрос 9 | `201 SessionDetails` (форма проверена); после этого владелец списка делает refetch (D-4) | `400 VALIDATION_FAILED` + `fieldErrors` (может быть без ключей: тогда ошибка уровня формы); `500 CREATE_SESSION_FAILED`; `409 COACH_SCHEDULE_CONFLICT` (опционально, обработать как общий `ApiError` без спец-логики); network; malformed | повторная отправка тех же введённых значений вручную. Автоповтора нет, идемпотентность не заявляется |

Особые случаи:
- **Сеть при POST:** исход неизвестен (запрос мог дойти до сервера). Клиент не утверждает "сессия не создана", пока не проверит список; текст сообщения решает UI. Контракт идемпотентности не даёт, поэтому после network/malformed ответа на POST разумно предложить пользователю проверить список перед повтором. Это формулировка для ui-designer и вопрос 9.
- **Неизвестный `error.code` с известным статусом** (например `418`, `404` на списке): `ApiError` как есть. Клиент не переименовывает и не группирует коды.
- **Ответ `200` со странной формой** (поле не того типа, нет `meta`, даты не ISO): `ResponseShapeError`. Частично валидные данные не показываются.
- **Лишние поля в ответе:** игнорируются (мы проверяем только используемые поля).
- **`error.code` пришёл не строкой / нет `message`:** malformed.

### 5. Даты (единая политика)

- Из API: все четыре поля (`startsAt`, `createdAt`, `updatedAt`, `cancellation.cancelledAt`) принимаются только как строки формата ISO 8601 UTC с `Z`. Проверка в маппере через `shared/lib/datetime`. Строка без `Z`/со смещением (`+02:00`) отвергается как malformed, потому что контракт требует именно UTC (подтвердить у владельца бэкенда, вопрос 2). В слое приложения значения остаются строками ISO; `Date` создаётся только внутри `shared/lib/datetime` для показа и вычислений.
- В API (форма → `startsAt`): локальные дата и время (из `<input type=date|time>` в часовом поясе браузера, A-1) → один `Date` → ISO UTC строка. Проверка "в будущем" делается по тому же `Date` против текущего момента (в тестах часы заморожены).
- Крайние случаи, которые должен учесть datetime-модуль: несуществующее локальное время (переход на летнее время, "дырка"): результат `Date` не совпадёт с введённым, это надо детектировать обратным разбором и считать ошибкой поля; неоднозначное время (осенний переход) допустимо, берётся первое по правилам `Date`; невалидная дата (30 февраля) → ошибка поля.
- Формат строки при отправке: развилка №7 (миллисекунды `.000Z` или без).
- Показ: только через `shared/lib/datetime` и `Intl`. Мок хранит и возвращает строки; сдвиг фикстур только в `mocks/` (AC-5.5).
- Ошибки: ошибка даты в ответе → `ResponseShapeError` (не "Invalid Date" в UI). Ошибка даты в форме → клиентская ошибка поля (не API-ошибка). `fieldErrors.startsAt` с сервера показывается так же, как другие ключи.

- Сценарии (см. таблицу выше):
  - `empty`: только `GET /api/sessions` возвращает пустой список (что после `POST` в этом сценарии, см. вопрос 10).
  - `list-error`, `coaches-error`, `create-error`: соответствующий запрос возвращает 500 с телом из JSON; остальные ведут себя как `normal`.
  - `details-error`: только `GET /api/sessions/ses_101`; детали других id работают как в `normal`.
- Тексты `message` берутся из `mock-scenarios.json` как есть: это значения сценариев, не придуманные коды.
- Приложение и клиент не знают, что запрос обслуживает мок. Единственная точка интеграции в рантайме: dev-bootstrap в `main.tsx` (D-5), который должен дождаться готовности worker до первого рендера, иначе первый запрос уйдёт мимо мока (особенно в StrictMode). Неперехваченные запросы к `/api` в режиме мока предпочтительнее трактовать как ошибку (`onUnhandledRequest: "error"`), чтобы пропуски были видны. Для ассетов Vite нужен bypass.

**Запуск с моками (по `package.json`)**
- Фактически команда есть: `npm run dev`. Для выбранного пути D-8 никакой новый скрипт не нужен: сценарий задаётся URL `?scenario=<name>` либо переменной окружения `VITE_MOCK_SCENARIO=<name> npm run dev` (Vite подхватывает `VITE_*` из окружения; не проверялось запуском).
- Чего нет и что нужно добавить как факт: скрипта `test` (его добавляет задача по D-9) и отдельного скрипта "запуск с моками/сценарием" (не обязателен). Я не предлагаю новых скриптов, кроме `test` из D-9. Какую команду считать "документированной" (Q-9), решает разработчик с coder.
- Что реально потребуется на этапе реализации: `src/mocks/` и dev-bootstrap в `main.tsx`; `public/mockServiceWorker.js` уже есть.

**`npm run build` и затем `npm run preview` при моках только в dev (D-8)**
- Что происходит:
  - `tsc -b` типизирует всё в `src/`, включая `mocks/` и JSON-фикстуры (если импорты JSON работают, см. выше о `resolveJsonModule`). Мок-код остаётся в проверке типов, но, если bootstrap делает условный динамический `import()` под `import.meta.env.DEV`, Vite удалит его из прод-бандла (tree-shaking). Фикстуры тогда в `dist` не попадают. Это ожидаемое поведение, но проверяется только фактической сборкой (не запускал).
  - `public/mockServiceWorker.js` копируется в `dist` как есть (статический файл). В бандле его никто не регистрирует, поэтому он инертен.
  - `vite preview` сервер не знает о `/api`. Для неизвестных путей `vite preview` по умолчанию отдаёт `index.html` со статусом 200 (SPA fallback). Поэтому `GET /api/sessions` вернёт HTML с 200, а не 404. Это не JSON, и клиент обязан превратить это в `ResponseShapeError` ("список не загрузился"), а не упасть при `JSON.parse`. Также `POST /api/sessions` на preview вернёт 404/405-подобный ответ (не проверялось). Итог: в preview приложение откроется, но список, детали, тренеры и создание будут в состоянии ошибки. Критерии AC-5.1 и AC-10.5 (работа "на моках без сети") в таком режиме не выполняются.
- Варианты и рекомендация: развилка №1.

## (в) Развилки (самые значимые первыми)

### 1. Build и preview без моков
- **Суть:** D-8 включает мок только в dev. Но `build` + `preview` — естественный "прод-подобный" запуск, а AC-11.2 требует воспроизводимой команды запуска. В preview приложение без бэкенда покажет ошибки везде.
- **Вариант A: моки только в dev, preview без бэкенда (как в D-8).** Документировать `npm run dev` как команду запуска, preview считать только проверкой сборки.
  - Плюсы: прод-бандл чистый (нет worker, фикстур), точно следует D-8, ничего лишнего.
  - Минусы: `npm run preview` показывает ошибки списка, браузерная верификация и демонстрация возможны только на dev-сервере; риск, что проверяющий запустит preview.
- **Вариант B: опциональный флаг сборки** (например `VITE_ENABLE_MOCKS=true` при `build`), включающий мок и в preview.
  - Плюсы: preview работает без бэкенда, любой режим воспроизводим.
  - Минусы: нарушает D-8 ("в проде мок не подключается") и требует правки архитектуры; мок-код и фикстуры попадают в бандл (при включённом флаге); граница "dev-инфраструктура" размывается; нужен новый env-флаг и документ.
- **Вариант C: A, плюс в README явно описать, что preview без моков показывает состояние ошибок (ожидаемое поведение), и добавить тест, что клиент выдаёт `ResponseShapeError` на HTML 200.**
  - Плюсы: честная документация, поведение предсказуемо, ничего не меняется в архитектуре.
  - Минусы: preview остаётся неинформативным.
- **Рекомендация: C** (A с документацией). Причина: решение D-8 принято пользователем, ассессмент проверяет приложение на моках через dev, а preview без бэкенда в любом случае не должен ломать клиент. Если нужна демонстрация preview, тогда B с отдельным решением архитектора.

### 2. Приоритет выбора сценария и невалидное имя
- **Суть:** D-8 задаёт `?scenario=` затем `VITE_MOCK_SCENARIO` затем `normal`. Не определено, что делать с неизвестным/пустым/повторным значением и с именами опциональных сценариев (`create-conflict` и т.д.), которые есть в JSON, но вне объёма.
- **Вариант A: невалидное имя в URL → предупреждение в консоль и откат на значение из env, затем `normal`.**
  - Плюсы: приложение не падает, видно в консоли, поведение мягкое.
  - Минусы: опечатка может незаметно дать `normal` (ложное впечатление, что сценарий включён).
- **Вариант B: невалидное имя → явная ошибка при старте (блокирующий экран/исключение до рендера) с перечнем допустимых имён.**
  - Плюсы: опечатка не пройдёт незамеченной, детерминированность.
  - Минусы: жёстче; нужно решить, где показывать ошибку (вне компонентов); для проверяющего лишний сбой.
- **Вариант C: невалидное имя → `console.warn` + `normal` и видимая метка не в UI, но в `console`/`window`-диагностике.**
  - (Близко к A, но без отката на env.)
- **Рекомендация: A** с явным `console.warn`, перечнем допустимых имён и фиксацией выбранного источника ("url" | "env" | "default"). Допустимыми считать ровно шесть обязательных имён; опциональные из JSON (`create-conflict`, ...) не поддерживаем и относим к невалидным. Причина: мок не должен ломать запуск, но молчаливый откат хуже предупреждения. Если пользователь хочет B, это тоже нормально.

### 3. Поведение `coaches-error` и повторов: статичная или "один раз падает" ошибка
- **Суть:** JSON-сценарии статичны: `coaches-error` возвращает 500 на каждый `GET /api/coaches`, значит "Повторить" в браузерном режиме никогда не восстановится. То же для `list-error`, `details-error`. Вопрос: нужен ли в моке путь "после повтора успех" для демонстрации восстановления.
- **Вариант A: детерминированно статично (как в JSON).** Восстановление проверяется в тестах через `server.use` (сначала ошибка, потом успех).
  - Плюсы: ровно по `mock-scenarios.json`, просто, детерминированно.
  - Минусы: в браузере восстановление не показать без смены сценария и перезагрузки.
- **Вариант B: ошибка только на первый запрос, затем успех.**
  - Плюсы: демонстрирует recovery.
  - Минусы: отходит от JSON ("returns 500"), недетерминирован при StrictMode (двойной эффект съест "первый" отказ), путает проверяющего.
- **Вариант C: статично, но смена сценария без перезагрузки через URL.** Это противоречит D-8 (читается один раз).
- **Рекомендация: A.** Причина: StrictMode и детерминированность; для проверки recovery в браузере достаточно открыть URL без `?scenario=error` после ошибки, а автотесты покрывают переход ошибка → успех.

### 4. Q-6, на какой границе ставится гарантия "не отправлять POST без валидного coachId"
- **Суть:** клиент API (`shared/api`) не знает загруженных тренеров. Гарантию можно ставить в разных местах.
- **Вариант A: guard в `useCreateSession` / фиче `create-session`:** `submit` не вызывает `createSession`, пока `coaches.status !== "success"` или `coachId` не входит в загруженный список. `shared/api` остаётся без этой логики.
  - Плюсы: сохраняется граница (shared не знает о доменной связи); тестируется через поведение: при `coaches-error` ни одного `POST`.
  - Минусы: гарантия живёт в фиче, а не на уровне транспорта.
- **Вариант B: guard только в UI (кнопка disabled).** Минусы: гарантия слабая, нет защиты на уровне вызова.
- **Вариант C: передавать список допустимых тренеров в `createSession`.** Минусы: затягивает доменную связь в shared.
- **Рекомендация: A** (плюс UI-блокировка со стороны ui-designer как дублирующий слой). Тест: при `coaches-error` нажатие "отправить" не создаёт `POST`.

### 5. Выбор формата возврата ошибок клиента
- **Суть:** бросать типизированные ошибки или возвращать union.
- **Вариант A: бросать** `ApiError | NetworkError | ResponseShapeError`; хуки ловят и кладут в `error`.
  - Плюсы: простой код вызовов, привычно для `async/await`; хуки так и так оборачивают в try/catch.
  - Минусы: типы ошибок не видны в сигнатуре; легко забыть `catch`.
- **Вариант B: возвращать `{ok:true,data} | {ok:false,error}`**. Плюсы: явная обработка, типобезопасно. Минусы: больше шаблонного кода; отмену надо отдельно кодировать.
- **Рекомендация: B для всего, кроме отмены (отмена бросается/сигнализируется отдельно)**, потому что D-7 формулирует "типизированный результат". Если писать хотят проще, A тоже ок. Принципиальной разницы для контракта нет.

### 6. Глубина валидации формы ответа
- **Суть:** без библиотеки валидации (zod и др. не добавлены, добавлять новую зависимость не предлагаю).
- **Вариант A: рукописные узкие проверки используемых полей и ISO-дат.** Плюсы: без зависимостей, соответствует D-6. Минусы: рукописный код, возможны пропуски.
- **Вариант B: только проверка ISO-дат и наличия `data/meta`, остальное доверять типам.** Плюсы: меньше кода. Минусы: "неверная форма" ловится частично (требование из задачи это покрывает слабо).
- **Рекомендация: A** (проверять все поля `SessionSummary`/`SessionDetails`/`CoachSummary`, которые рендерятся, плюс enum-значения `type/status/visibility`). Неизвестное значение enum: считать malformed (а не показывать как есть), либо терпимо пропускать. Это уточнение для вопроса 5 ниже: я склоняюсь к malformed, но нужна ваша позиция, так как `full`/будущие статусы могут появиться.

### 7. Формат `startsAt` при отправке
- **Суть:** `Date#toISOString()` даёт `...:00.000Z`, фикстуры без миллисекунд.
- **Вариант A: отправлять как есть (`.000Z`).** Плюсы: стандартный ISO UTC, меньше кода. Минусы: формат отличается от фикстур; мок/бэкенд должны принимать оба.
- **Вариант B: отрезать миллисекунды → `YYYY-MM-DDTHH:mm:ssZ`.** Плюсы: совпадает с фикстурами. Минусы: лишняя трансформация.
- **Рекомендация: B,** и мок (и маппер входящих дат) принимает оба варианта (с дробной частью и без). Причина: фикстуры показывают предпочтительный формат, секунды форма всё равно не задаёт.

### 8. Сортировка и `total > pageSize` после создания
- **Суть:** контракт: `pageSize: 10`, пагинация вне объёма (A-4). Если пользователь создаст 6+ сессий, `data` в моке станет >10.
- **Вариант A: не усекать, отдавать все, `total` = фактическое число, `pageSize` остаётся 10.** Плюсы: созданные сессии всегда видны (AC-3.13). Минусы: ответ формально нарушает `pageSize`.
- **Вариант B: усекать до 10.** Плюсы: формально верно. Минусы: новая сессия может не показаться в списке, что ломает AC-3.13.
- **Рекомендация: A,** порядок: фикстуры в исходном порядке, новые в конец (контракт сортировку не задаёт, assumed). Клиент не опирается на `pageSize` для показа и не обрабатывает пагинацию. Подтвердить у владельца (вопрос 8).

### 9. `create-error` и `empty`: порядок и взаимодействие
- **Суть (a):** `create-error` для любого `POST` 500, или сначала валидация (тогда невалидный запрос даёт 400, а валидный 500)?
  - Вариант A: любой `POST` → 500 (по JSON, статично). Плюс: просто, детерминированно. Минус: нельзя в этом сценарии увидеть `400`.
  - Вариант B: сначала валидация, потом 500. Плюс: ближе к реальному бэкенду. Минус: выдумываем порядок.
  - Рекомендация: A (ошибку 400 проверять в тестах через `server.use`).
- **Суть (b):** в `empty` после успешного `POST` список остаётся пустым или показывает созданную?
  - Вариант A: список = пустой статичный ответ по JSON. Минус: нарушает "созданная сессия видна" в этом сценарии, то есть путь "создать из пустого состояния" (AC-4.3) не закончится видимым результатом.
  - Вариант B: `empty` = стартовое состояние хранилища (нет сессий), `POST` добавляет, и список показывает созданное.
  - Рекомендация: B. Это сохраняет AC-3.13 и AC-4.3 (путь "создать сессию" имеет смысл), а JSON описывает именно стартовый ответ. Подтвердить у пользователя, поскольку JSON формально статичен.

### 10. POST и отмена запроса
- **Суть:** при закрытии формы во время `pending` отменять запрос через `AbortController` или нет.
- **Вариант A: не отменять POST,** просто игнорировать результат после размонтирования. Плюсы: нет ложного "не создано" (сервер мог уже создать). Минусы: результат теряется, если форму закрыли.
- **Вариант B: отменять.** Плюсы: единообразие с GET. Минусы: клиент не знает исхода, а контракт идемпотентности не даёт.
- **Рекомендация: A** (отмена только для GET). Причина: мутации нельзя безопасно "откатить" клиентской отменой. Если форма закрыта, а `201` пришёл, владелец списка всё равно делает refetch.

## (г) Черновая позиция

### Q-3 (выбор сценария), на уровне контракта
- **Источник и приоритет:** `?scenario=<name>` в URL, затем `VITE_MOCK_SCENARIO`, затем `normal` (D-8). Читается один раз в `src/mocks` до первого рендера; влияет на мок только на старте. Смена имени после старта игнорируется (чтобы изменение URL приложением не меняло мок). Перезагрузка с тем же URL даёт тот же сценарий.
- **Допустимые имена:** шесть обязательных. Остальные (в том числе опциональные из JSON) и пустые значения невалидны (развилка №2, моя рекомендация A: предупреждение и откат).
- **Только dev:** `import.meta.env.DEV`; в тестах переменная и URL не используются, сценарии задаются `server.use` поверх базовых обработчиков.
- **Сочетание с маршрутизацией и фильтрами:**
  - Параметр `scenario` соседствует с `query` и `status`. Слой `shared/router` не знает его имени, но сохраняет посторонние параметры при навигации (AC-1.14). Домен (`features/sessions`) читает только `query` и `status`.
  - "Сбросить все фильтры" удаляет только `query` и `status`; `scenario` остаётся. Тест на это нужен (AC-1.13, AC-1.14).
  - Редирект неизвестного пути на `/sessions` (D-3) должен сохранять `search`. Порядок старта: сначала `mocks` читает URL, затем рендерится приложение, поэтому ранний редирект параметр не потеряет, но проверить.
  - В запросы `GET /api/sessions` `scenario` не передаётся (клиент строит query только из `query` и `status`).
- **Чтобы не было утечки в компоненты:**
  - Компоненты, хуки и `shared/api` не импортируют `mocks/` и не читают `scenario` и `VITE_MOCK_SCENARIO`.
  - Единственный потребитель `mocks/` в рантайме: dev-bootstrap `main.tsx`. Тесты подключают `mocks/` через setup.
  - Никаких контролов выбора сценария и индикаторов "mock mode" в UI. Для видимости допустим `console.info` с выбранным сценарием и источником.
  - Проверка на ревью: grep по `scenario` и `fixtures` вне `src/mocks` и тестового setup должен быть пуст.

### Q-6 (`GET /api/coaches` упал, а пользователь пытается создать сессию), только API
- **Гарантии клиента:**
  1. `createSession` не вызывается (и `POST` не уходит), пока нет успешно загруженного списка тренеров и выбранный `coachId` не содержится в нём. Гарантия ставится в `useCreateSession` / фиче `create-session` (развилка №4, вариант A), а не в `shared/api`.
  2. Что считается валидным `coachId`: непустая строка, равная `id` одного из элементов последнего успешного ответа `GET /api/coaches`. Свободный ввод `coachId`, значения по умолчанию, "первый тренер" и значения из прошлых сессий не допускаются. Если список успешно загружен, но пуст: валидного `coachId` нет, отправка невозможна.
  3. Повтор загрузки: `useCoaches().retry()` по явному действию пользователя; автоповторов нет. Повтор отменяет предыдущий незавершённый запрос; после успеха ранее введённые значения формы не сбрасываются (это ответственность формы, но API-слой не должен для этого делать ничего особенного).
  4. Если выбранный ранее `coachId` отсутствует в обновлённом списке после повтора, он перестаёт быть валидным (форма должна сбросить выбор; решение ui-designer).
  5. Сервер всё равно проверяет `coachId` (`400 VALIDATION_FAILED` с `fieldErrors.coachId`, assumed ключ). Клиентская проверка не заменяет серверную и не должна скрывать серверную ошибку.
- **Что API-слой не решает:** блокировать форму целиком или только поле тренера, тексты, расположение "Повторить" (это Q-6 в части UI за ui-designer; D-7 уже требует "выбор недоступен, отправка заблокирована, повтор есть").
