Статус: решения подтверждены пользователем лично. Роль: architect. Код, зависимости, конфиги, requirements.md и specs/ этим документом не изменяются.
Входы: requirements.md, API_CONTRACT.md, MOCKING_GUIDE.md, package.json, vite.config.ts, src/ (шаблон Vite), rulesets common/framework (project пуст).

## 0. Факты о репозитории (основа решений)

- dependencies: react, react-dom (React 19). devDependencies: vite, @vitejs/plugin-react, typescript, oxlint, msw 2.14.6, типы. Скрипты: dev, build, lint, preview.

## 1. Решения

### D-1. Формат деталей: модальное окно на маршруте /sessions/:id (Q-1, вариант M1)
- Детали открываются в модальном окне поверх смонтированного списка. Адрес: `/sessions/:id`. Список живёт на `/sessions`.
- Query string общий для списка и деталей: `/sessions/:id?query=..&status=..`. Открытие деталей из списка сохраняет query string; закрытие возвращает на прежний URL списка.
- Диалог: нативный `<dialog>` с `showModal()` (фокус-ловушка, inert фона, Esc, возврат фокуса). Самописная ловушка фокуса не делается. React управляет диалогом через ref и эффект (`showModal()` при монтировании, `close()` при размонтировании). Есть `aria-labelledby` на заголовок и видимая кнопка закрытия.
- Закрытие: Esc (событие `cancel` перехватывается), кнопка закрытия и кнопка "Назад" браузера идут через одну навигацию; URL остаётся единственной истиной видимости модалки.
- Возврат: различаются "пришли из списка" (в `history.state` флаг, что предыдущая запись принадлежит приложению и это список) и "зашли напрямую". Из списка закрытие выполняет `history.back()`. При прямом заходе закрытие выполняет `replace` на `/sessions` с сохранённым query string.
- Прямой заход на `/sessions/:id`: открывается список (с фильтрами из query string) и поверх него модалка с деталями. Deep link (AC-2.5) выполнен без ограничений.
- Выбор "модалка или drawer" остаётся предварительно модалкой; визуальные и интерактивные детали, включая фокус при deep link, за ui-designer. Архитектура не меняется при замене на drawer (URL-управляемость сохраняется).

### D-2. Фильтры живут в query string (Q-2)
- `query` и `status` хранятся только в URL. URL — единственный источник истины. Список выводит параметры запроса `GET /api/sessions` из URL, отдельной копии в состоянии нет.
- Поле поиска держит transient-значение (то, что печатает пользователь) и записывает его в URL с debounce через `replace`, чтобы Назад не шёл по символам. Смена статуса записывается единообразно (рекомендуется `replace`; окончательное для writing-plans, без расхождений между фильтрами).
- Невалидный `status` нормализуется на чтении: неизвестное значение трактуется как "нет фильтра" и не уходит на сервер (иначе `400 INVALID_FILTER`). Пустой или пробельный `query` трактуется как отсутствие.
- Сброс фильтров очищает `query` и `status` в URL.
- Решение пользователя: URL-синхронизация фильтров ВКЛЮЧЕНА в требования. Это расширение объёма относительно текущего requirements.md, где она исключена как опциональная. Нужные правки перечислены в разделе 9 и выполняются requirements-analyst отдельным запуском.
- Слой History API нужен независимо от формата деталей (чтение и запись query string), поэтому выбор M1 не добавляет отдельного класса кода.

### D-3. Самописный тонкий слой History API
- Без новых зависимостей, нативные `history.pushState/replaceState` и событие `popstate`.
- Размещение: `shared/router/` (общая инфраструктура навигации без знания о доменах). Интерфейс минимальный: чтение `location` (path + search) с подпиской, `navigate(to, { replace, state })`, разбор пути `/sessions/:id`, чтение и запись search-параметров, флаг "из приложения" в `history.state`.
- Слой не знает о фильтрах и сценариях. Доменные соглашения об именах параметров (`query`, `status`) живут в `features/sessions`.
- Запрещено разрастание в мини-роутер: вложенные маршруты, loader-ы, гварды не вводятся. Неизвестные пути ведут на `/sessions` через `replace`.
- Слой не должен ломаться и не должен тащить посторонние параметры (в том числе `scenario`, см. D-8) дальше как параметры фильтра: домен читает только `query` и `status`, остальные параметры слой сохраняет нетронутыми при навигации.

### D-4. Серверное состояние: хуки по ресурсу (выбор A)
- Хуки на `useState`/`useEffect` с `AbortController`, явные статусы `idle | loading | success | error`: `useSessions(filters)`, `useSessionDetails(id)`, `useCoaches()`, `useCreateSession()`.
- Один владелец на ресурс, общего кэша нет. Детали всегда запрашиваются через `GET /api/sessions/:id` и не собираются из строки списка. Тренеры загружаются при открытии формы создания, а не глобально.
- После успешного создания список перезапрашивается (счётчик-инвалидатор или явный `refetch` в владельце списка). Созданная сессия в список вручную не вставляется.
- Отмена: при смене фильтров, id или размонтировании запрос отменяется; ответ отменённого запроса игнорируется (в том числе под StrictMode).
- Повтор: каждый хук предоставляет `retry`.
- Дублирования источников истины нет: фильтры = URL, список/детали/тренеры = свои хуки, форма = локальное состояние формы.

### D-5. Структура папок и границы
```
src/
  app/                  композиция, провайдеры, выбор маршрута (/sessions, /sessions/:id), bootstrap мока в main.tsx
  features/
    sessions/           список, фильтры, строка/карточка, модалка деталей, хуки useSessions/useSessionDetails, чтение/запись фильтров в URL
    create-session/     форма, чистый валидатор, useCreateSession, useCoaches (или в sessions, если используется только формой; решает плановый шаг)
  shared/
    api/                HTTP-клиент, типы контракта, мапперы, ApiError
    router/             тонкий слой History API
    lib/                datetime (единственная точка работы с датами)
    ui/                 только реально переиспользуемое
  mocks/                handlers, loader фикстур, fixture clock, выбор сценария, setup msw/node
  test/                 setup vitest (полифил showModal при необходимости)
```
Направление зависимостей: `app` -> `features` -> `shared`. Фичи не импортируют друг друга; связь через `app` (колбэки, props). `shared` не импортирует `features` и `app`. `mocks/` не импортируется никем, кроме точки bootstrap в `main.tsx` и тестового setup. Компоненты и `shared/api` не импортируют JSON-фикстуры и не ветвятся по именам сценариев (AC-5.3).

### D-6. Даты
- Единственная точка: `shared/lib/datetime`. Мапперы `shared/api` проверяют, что `startsAt`, `createdAt`, `updatedAt`, `cancellation.cancelledAt` являются валидными ISO 8601 UTC, и отвергают иное как ошибку формы ответа.
- Показ только через модуль (Intl, часовой пояс браузера, допущение A-1). Преобразование формы (локальные дата и время -> ISO UTC для `startsAt`) и проверка "в будущем" живут там же. Прочий код не вызывает `new Date(...)` и `toLocale*` напрямую.
- Сдвиг фикстурного времени только в `mocks/`; приложение получает обычные ISO-строки (AC-5.5). Тесты замораживают время и применяют то же преобразование из `mocks/`.

### D-7. Ошибки и fieldErrors
- `shared/api` превращает ответ в типизированный результат: `ApiError` (`code`, `message`, `fieldErrors`, статус) и отдельный вид для сетевой ошибки. Транспортные вызовы только здесь (AC-5.6).
- Хуки держат статус и ошибку. UI выводит ошибку рядом с границей восстановления:
  - list-error: в области списка, с "Повторить"; приложение и фильтры остаются доступными;
  - details-error (включая 404 `SESSION_NOT_FOUND`, A-8): внутри модалки, с "Повторить" и закрытием;
  - coaches-error: в форме; выбор тренера недоступен, отправка заблокирована, есть "Повторить загрузку тренеров"; форма не делает вид, что можно выбрать тренера (AC-3.14). Блокировка всей формы или только поля — решение ui-designer (Q-6);
  - `fieldErrors` (400 `VALIDATION_FAILED`): у соответствующих полей (`aria-invalid`, `aria-describedby`); ключи без поля и ошибки 500 `CREATE_SESSION_FAILED`/сеть — ошибка уровня формы в области формы с live-region; введённые значения не сбрасываются (AC-3.11);
  - общий error boundary в `app` только страховка, не заменяет локальную обработку.
- Валидация формы (AC-3.1–3.8) — чистая функция в `features/create-session`, без библиотеки; серверные `fieldErrors` накладываются поверх клиентских.
- Защита от дублей: флаг pending в `useCreateSession` блокирует повторный вызов и отключает кнопку; идемпотентность не изображается (AC-3.10).
- Статус `full` берётся из API (A-2). Успех создания даёт явное подтверждение (live-region); действие "открыть новую сессию" или сброс фильтров — за ui-designer (Q-5), навигацию выполняет `app` через слой D-3.

### D-8. Выбор сценария мока (Q-3)
- `?scenario=<name>` читается один раз при старте внутри `src/mocks`, до рендера приложения. `VITE_MOCK_SCENARIO` — значение по умолчанию (по умолчанию `normal`). Включено только в dev (`import.meta.env.DEV`); в проде мок и чтение параметра не подключаются.
- Документируется в README как assessment-инфраструктура, не продуктовая функция. Контролов выбора сценария в UI нет.
- `?scenario=` соседствует с query-параметрами фильтров в URL. Изоляция: читает только `mocks/`; слой D-3 сохраняет посторонние параметры при навигации (чтобы `scenario` не терялся при переходах) и не включает их в фильтры; домен читает только `query` и `status`. Параметр читается один раз, поэтому последующее присутствие или потеря в URL на работу мока не влияет.
- В тестах сценарий задаётся явно через `server.use(...)` из `msw/node`.
- Реализация обработчиков и деталей механизма — за api-integration.

### D-9. Тесты (4 новые dev-зависимости)
Стек: `vitest`, `@testing-library/react`, `@testing-library/user-event`, `jsdom`; `msw/node` из уже установленного пакета `msw`. `@testing-library/jest-dom` НЕ добавляется (решение пользователя); проверки пишутся стандартными утверждениями vitest и запросами Testing Library (роли, имена, `toBeTruthy`/свойства DOM, `getByRole`/`findByRole`). Новых зависимостей ровно четыре; версии определит установка, в документе не фиксируются.

Причина (AC-10.4): в репозитории нет раннера и DOM-окружения, а AC-9.1/9.3 требуют автотестов поведения через ту же HTTP-границу, что и приложение (MSW).
Компромисс: четыре новые dev-зависимости; jsdom не вычисляет layout и может неполно реализовывать `<dialog>.showModal()`; без jest-dom утверждения о состоянии DOM немного многословнее; визуальная адаптивность и реальный фокус проверяются отдельно в браузерной верификации.
Правка `vite.config.ts` (секция test: окружение jsdom, setup-файл, при необходимости `globals`) необходима для запуска раннера и минимальна; другие конфиги не меняются (AC-10.3). Добавляется скрипт `test` в package.json (также изменение конфигурации, часть той же необходимости).
Риск `showModal` в jsdom: если метод отсутствует или неполон, в `src/test/` setup-файле добавляется тонкий полифил (устанавливает `open`, вызывает `close`-событие); это не библиотека и не логика приложения. Поведение фокус-ловушки в браузере проверяется в browser-verify, а не в jsdom.

Набор: 6–7 интеграционных тестов (рендер приложения + `msw/node`, время заморожено, то же преобразование fixture clock):
1. Начальная загрузка (loading), затем список с полями AC-1.2.
2. Поиск и фильтр по статусу уходят в `GET /api/sessions` параметрами `query`/`status`; сброс возвращает полный список.
3. `empty`: "сессий нет" с путём создания; отдельно: фильтры без совпадений дают другое сообщение и сброс.
4. `list-error` (или `details-error`): понятное сообщение и "Повторить".
5. Создание: ошибки валидации у полей, успешная отправка с подтверждением, одна `POST` при повторном клике во время ожидания.
6. `create-error` 500: ввод сохранён, понятное сообщение; 400 `fieldErrors` показаны у полей.
7. Восстановление фильтров из URL при прямом заходе и навигация деталей (открытие меняет URL и сохраняет query, deep link открывает диалог, закрытие возвращает на прежний URL списка). При необходимости тест 7 разбивается на два, но общее число остаётся в рамках оправданного риска.
Юнит-тесты валидатора и дат — только при оправданном риске (AC-9.2).

## 2. Обоснование
- Требования AC-1.8, AC-2.4, AC-2.5 и решение 2B (URL как состояние фильтров) выполняются единым механизмом: URL как источник истины видимости модалки и фильтров.
- Правила Common: одно состояние — один владелец, разделять transient UI, URL, remote; отказ от новой библиотеки для обратимой локальной задачи.
- Нативный `<dialog>` заменяет самописную фокус-ловушку и снижает риск ошибок доступности без зависимостей.

## 3. Затронутые границы
- UI (features) / навигация (shared/router) / интеграция (shared/api) / мок (mocks) / композиция (app) разделены; тесты используют `mocks/` и `msw/node` только через setup.
- Граница с ui-designer: форма и поведение модалки, композиция, состояния, фокус при deep link, тексты.
- Граница с api-integration: клиент, мапперы, обработчики MSW, fixture clock, механизм сценариев, формат ошибок.

## 4. Правила зависимостей
- `app` -> `features` -> `shared`; обратных импортов нет; `features` друг друга не импортируют.
- Только `shared/api` вызывает `fetch`. Только `shared/lib/datetime` работает с датами. Только `mocks/` знает о фикстурах, сценариях и сдвиге времени.
- `shared/router` не знает доменных имён параметров; `features/sessions` владеет `query`/`status`.
- Единственный потребитель `mocks/` в рантайме — bootstrap `main.tsx` (dev); тесты подключают `mocks/` через setup.

## 5. Риски
- Расхождение URL и видимости модалки (Esc, Назад, закрытие кнопкой): смягчается единым путём закрытия через навигацию и тестом 7.
- Определение "пришли из списка" при reload и многовкладочных сценариях: при отсутствии флага в `history.state` действует поведение прямого захода (`replace` на список).
- Debounce поиска и гонки запросов: смягчается `AbortController` и игнорированием устаревших ответов.
- jsdom и `showModal`: см. D-9.
- Чувствительность "даты в будущем" к часам: время замораживается.
- Разрастание самописного слоя маршрутизации: ограничено в D-3.
- Параметр `scenario` в URL рядом с фильтрами: см. D-8.
- StrictMode дублирует эффекты: хуки обязаны быть идемпотентными и отменяемыми.

## 6. Отвергнутые альтернативы
- Отдельная страница деталей (размонтирует список) — хуже для AC-1.8/2.4.
- Деталь без URL (M2) — нет deep link, Назад не закрывает модалку.
- Drawer как основной формат — не отвергнут окончательно, остаётся визуальной заменой модалки (D-1); архитектура не меняется.
- Фильтры только в памяти или в глобальном Context — противоречит выбору пользователя 2B.
- Собственный кэш/store или `use()` + Suspense вместо хуков — избыточно или тоньше для тестов.
- Самописная фокус-ловушка вместо `<dialog>` — больше кода и рисков.
- `@testing-library/jest-dom`, happy-dom, только браузерные проверки — не выбраны пользователем / не проходят AC-9.1.
- Выбор сценария только через env или localStorage — неудобно для верификации и скрытое состояние.
- Новый роутер или data-библиотека — не предлагаются (факт-ограничение: их в репозитории нет).

## 7. Следствия для реализации
- Добавить dev-зависимости (имена без версий): vitest, @testing-library/react, @testing-library/user-event, jsdom; скрипт `test`; секция test в `vite.config.ts`; setup-файл с подключением `msw/node`, заморозкой времени и при необходимости полифилом `showModal`.
- Каждая зависимость и правка конфига записываются с причиной и компромиссом в артефактах (AC-10.4).
- Модалка деталей рендерится при совпадении маршрута `/sessions/:id`; заголовок и роль диалога доступны; закрытие всегда идёт через навигацию.
- Все параметры запроса списка выводятся из URL; поле поиска имеет локальное значение и debounce-запись `replace`.
- Невалидные значения `status` из URL нормализуются до запроса.
- `scenario` читается только в `mocks/`; слой маршрутизации сохраняет посторонние параметры.
- README: команда запуска и описание `?scenario=`/`VITE_MOCK_SCENARIO` как assessment-инфраструктуры (Q-9 — за разработчиком и coder).

- Q-3 (выбор сценария): закрыт. `?scenario=<name>` читается один раз при старте в `src/mocks`, `VITE_MOCK_SCENARIO` как значение по умолчанию (`normal`), только dev, документируется как assessment-инфраструктура, в тестах `server.use`; слой маршрутизации сохраняет `scenario` нетронутым и не трактует его как фильтр; чтение изолировано в `mocks/`.
